1. The big picture

Five pieces. One Python API in the middle talks to three helpers.

FastAPI

The API

Receives requests, checks them, and coordinates everything. This is the code in this repo.

PostgreSQL

The record keeper

Stores every incident and document. This is the source of truth: if anything else is lost, it can be rebuilt from here.

Ollama

The meaning translator

A local AI model (nomic-embed-text) that turns text into 768 numbers (an embedding). Similar meaning gives similar numbers.

Qdrant

The similarity finder

A vector database (runs in Docker). Stores each incident's 768 numbers and quickly finds the closest ones to a question.

Client

You

A browser, curl, or Swagger at /docs. A frontend comes in a later phase.

The one idea to remember

Postgres holds the facts. Qdrant holds the meaning. The same UUID links them.

Why separate layers?

Routes know HTTP. Repositories know the database. Services know Ollama and Qdrant. Changing one (say, swapping the vector database) does not touch the others, and each can be tested alone.

Who owns the transaction?

Not the repository. get_session in api/deps.py opens one database session per request, commits if the request succeeds, and rolls back if anything raises.

Index: (service, reported_at), for "incidents of service X, newest first".

Table documents (runbooks and guides) has the same style: title, doc_type, optional service, content, source, tags, created_at.

Qdrant

Collection incidents (one point per incident)

{
  "id":      "b2a5b49a-…-91b3e5",   // same UUID as Postgres
  "vector":  [0.012, -0.34, …],     // 768 numbers from Ollama
  "payload": {
    "service":     "payment-service",
    "severity":    "SEV2",
    "status":      "open",
    "tags":        ["deploy"],
    "reported_at": "2026-01-02T10:00:00+00:00"
  }
}
  • What is turned into numbers: title + description + root cause + resolution.
  • What stays as payload: service, severity, status, tags. They are used to filter, not to measure meaning.
  • Similarity uses cosine distance: 1.0 means same direction, 0 means unrelated.
Qdrant code ready, collection not created yet

Collection document_chunks (one point per chunk)

{
  "id":      "uuid5(document id, chunk number)",   // always the same for the same chunk
  "vector":  [0.03, -0.11, …],                      // 768 numbers for title + chunk text
  "payload": {
    "document_id": "123e4567-…",                    // the link back to PostgreSQL
    "chunk_index": 2,  "chunk_count": 5,
    "title":    "DB failover runbook",
    "doc_type": "runbook",
    "service":  "payment-service",                   // null = applies to every service
    "source":   "runbooks/failover.md",
    "text":     "Promote the replica to primary …"   // the passage: usable as a citation
  }
}
  • A document becomes many points, so a point id can no longer be the document id. The document id moves into the payload.
  • Long documents are cut into chunks so each vector means one topic, instead of a blurry average of everything.

6. Design decisions, in plain words

Postgres is the boss

Qdrant can always be rebuilt from Postgres (reindex). So Postgres decides what exists.

Same UUID in both

The Postgres id is the Qdrant point id. Re-indexing the same incident overwrites its point instead of creating a duplicate.

Indexing is "best effort"

If Ollama or Qdrant is down, the incident is still saved (a warning is logged). Recording an incident must work during an outage. Missed ones are fixed by reindex.

Two models per concept

Incident (Pydantic) is the API contract with rules. IncidentRecord (SQLAlchemy) is the table. A mapper converts between them, so each can change independently.

Rules at the edge

Bad input (too long, resolved without a date) gets a clear 422, never a database error. The DB also has CHECK constraints as a safety net.

Outages are 503, not 500

If search cannot reach Ollama or Qdrant, the client sees "temporarily unavailable", which is honest: it is not their mistake.

Qdrant instead of pgvector

Chosen for built-in hybrid search and filtering. The price: two stores to keep in sync.

Tests never touch real data

Database tests roll back; Qdrant tests use temporary collections that are deleted. The real incidents collection is never used by tests.

Chunk documents, not incidents

An incident is short, so one incident is one vector. A runbook covers many topics, so it is cut into chunks and each chunk gets its own vector. In a small test, the matching chunk scored higher than the whole document every time.

Deterministic chunk ids

A chunk's id is made from the document id and the chunk number, so indexing again overwrites instead of duplicating. The document id also sits in the payload to find all of a document's chunks.

Global documents match every service

A runbook with no service applies everywhere, so filtering by a service still returns it.

Measure search, don't eyeball it

100 seeded incidents with known answers and a script that counts how often the right scenario comes first. Now every future change (hybrid search, reranking) can be compared with a number.

7. What is done, and what is not

✔ Working now

  • Incident and document models with validation
  • PostgreSQL tables, with two Alembic migrations
  • Create, get, and list for incidents and documents
  • Embeddings through Ollama (768 dimensions)
  • Qdrant running in Docker, collection with filters
  • Automatic indexing of new incidents
  • Semantic search over incidents, with filters
  • Reindex script
  • Document chunking, indexing and best-passage search (as a service layer, tested with real Ollama and Qdrant)
  • 100 seeded test incidents in PostgreSQL and Qdrant, plus an evaluation script (18 of 20 questions had the right scenario first in a first run on synthetic data)
  • 210 tests passed in the last full run (they use real Postgres, Qdrant and Ollama)

⏳ Not built yet

  • Documents in the API: POST /documents does not index yet, and there is no /search/documents
  • A simple UI (search box, filters, results table)
  • Hybrid search (keywords + meaning) and reranking
  • An AI-written answer with citations (the "G" in RAG)
  • Multi-source investigation (LangGraph)
  • Login, roles, and document permissions
  • Metrics, observability, full Docker deployment
Today the system finds similar incidents through the API. Documents can be indexed and searched in code, but not through the API yet. It does not write an answer yet.

8. Run it yourself

source .venv/bin/activate
docker compose up -d                    # start Qdrant
ollama pull nomic-embed-text            # once
alembic upgrade head                    # create tables
python -m app.scripts.seed_incidents    # 100 test incidents into Postgres + Qdrant
python -m app.scripts.evaluate_search   # how often is the right scenario first?
python -m app.scripts.seed_incidents --clean   # remove only the seeded incidents
python -m app.scripts.reindex           # rebuild the Qdrant index from Postgres
python -m uvicorn main:app --reload     # add --port 8001 if 8000 is busy
python -m pytest                        # run all tests

Then open /docs in the browser to try the endpoints.

9. Explaining it to someone else

30 seconds

"OpsMind is a backend that helps engineers during outages. You store past incidents. When something breaks, you describe it in plain words and it finds the most similar past incidents, even if the wording is different, by comparing meaning instead of keywords."

2 minutes

"Incidents are saved in PostgreSQL, which is the source of truth. When one is saved, the text is sent to a local AI model, Ollama, which turns it into a list of 768 numbers that captures its meaning. Those numbers go into Qdrant, a vector database, under the same ID. When someone searches, the question goes through the same model, Qdrant finds the closest stored vectors, and then I load the full incidents from Postgres and return them ranked, with filters like service or severity."

"If the AI side is down, incidents are still saved, and a reindex script catches up later. Long runbooks are cut into chunks, each with its own vector, so a search can point at the exact passage. That already works as a service, but is not in the API yet. To test properly, I load 100 synthetic incidents and measure how often the right kind of incident comes first: about 90 percent in a first run, on synthetic data. The next steps are wiring documents into the API, a simple UI, and then generating a cited answer with an LLM."

Words that may come up

  • Embedding / vector: a list of numbers that represents the meaning of a text.
  • Cosine similarity: how close two vectors point, from 0 (unrelated) to 1 (same).
  • Payload: extra data stored next to a vector, used for filtering.
  • RAG: Retrieval-Augmented Generation: first retrieve relevant facts, then let an LLM answer using only those. Retrieval is built; generation is not.
  • Migration (Alembic): a versioned change to the database schema, like Flyway.
