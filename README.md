# 🛠 OpsMind AI — Enterprise Incident Intelligence

> A production-oriented Enterprise RAG system built using Python, FastAPI, PostgreSQL, and Qdrant that helps engineering teams investigate incidents using historical incident reports, runbooks, troubleshooting guides, and technical documentation, with grounded answers and citations.

> **Status:** Phase 1 (Knowledge Foundation) is in progress. Sections marked **Planned** describe the target design and are not implemented yet.

---

# 📌 Overview

During an outage, the answer usually already exists somewhere: a past incident report, a runbook, or a troubleshooting guide. Finding it by hand under pressure is slow.

OpsMind AI is designed to let an on-call engineer ask:

> *"payment-service is returning 503s after the deploy. Has this happened before?"*

and receive a **grounded answer** built only from retrieved company knowledge, with **citations** to the source incidents and documents.

This project is built step by step as a hands-on way to learn **Enterprise RAG engineering**:

- FastAPI
- Pydantic
- SQLAlchemy 2.x
- Alembic
- PostgreSQL
- Qdrant *(planned)*
- AWS Bedrock / Claude *(planned)*
- LangGraph *(planned)*

# 🚀 Features

## ✅ Implemented (Phase 1)

### 🧱 Incident Domain Model

The incident is modelled with Pydantic and enforces business rules at the boundary.

- `Incident`, `IncidentCreate`, and a shared `IncidentBase`
- `Severity` enum (`SEV1` – `SEV4`)
- `IncidentStatus` enum (`open`, `mitigated`, `resolved`)
- Timezone-aware datetimes normalized to UTC
- `resolved_at` must not be earlier than `reported_at`
- Status consistency rule: `resolved` ⇔ `resolved_at` is set

```text
Request JSON
     │
     ▼
IncidentCreate (Pydantic)
     │  validates fields and business rules
     ▼
Incident (server-generated UUID)
```

---

### 🗄 Persistence Layer

```text
Incident (Pydantic DTO)
        │
        ▼
     Mapper
        │
        ▼
IncidentRecord (SQLAlchemy ORM)
        │
        ▼
PostgreSQL "incidents" table
```

- SQLAlchemy 2.x typed ORM (`Mapped` / `mapped_column`)
- `TIMESTAMPTZ` datetimes, native `UUID` primary key
- `tags` stored as a PostgreSQL `ARRAY`
- `CHECK` constraints for severity and status, built from the domain enums
- Composite index `(service, reported_at)` for "incidents for service X, newest first"

---

### 🔁 Database Migrations

Schema changes are versioned with Alembic.

- `alembic/env.py` reads the DB URL from application settings (`.env`), not from `alembic.ini`
- Autogenerated migration reviewed before applying
- Working `upgrade` and `downgrade`

---

### 📦 Repository Pattern

```text
API Endpoint
     │
     ▼
IncidentRepository(session)
     │
     ▼
Mapper  ──>  IncidentRecord  ──>  PostgreSQL
```

- The repository accepts and returns domain `Incident` objects
- ORM objects never leave the repository
- The repository **flushes but never commits**: the caller owns the transaction

### 🌐 Incident API

| Method | Path | Description |
|---|---|---|
| `GET` | `/health` | Application health |
| `GET` | `/health/database` | Database connectivity check |
| `POST` | `/incidents` | Create an incident (server generates the id) |
| `GET` | `/incidents/{id}` | Fetch one incident (404 if unknown) |

```text
Request
   │
   ▼
FastAPI Router
   │
   ▼
get_session (one transaction per request)
   │      commit on success / rollback on error
   ▼
IncidentRepository
```

## Current

```text

                     FastAPI

                        │
                        ▼
                   get_session
                        │

                        │
                        ▼
                      Mapper

```

## Target

```text
                     Client
                        │
                        ▼
                     FastAPI
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   Incident API    Ingestion API     Query API
        │               │                │
        ▼               ▼                ▼
   PostgreSQL ◄──── Embeddings ────► Qdrant
 (source of truth)                  (vectors + payload)
                                         │
                                         ▼
                              Hybrid Retrieval + Rerank
                                         │
                                         ▼
                                LLM (Bedrock / Claude)
                                         │
                                         ▼
                             Grounded Answer + Citations
```

**Design decision:** PostgreSQL stays the source of truth for incidents. Qdrant stores vectors and search payloads, and the incident UUID is reused as the Qdrant point ID so the two stores stay linkable.

# 🔄 Workflow

## Create an Incident

```text
POST /incidents
      │
      ▼
IncidentCreate validation (422 on rule violation)
      │
      ▼
Generate UUID  →  Incident
      │
      ▼
IncidentRepository.add()  →  INSERT (flush)
      │
      ▼
get_session commits  →  201 Created
```

## Fetch an Incident

```text
GET /incidents/{id}
      │
      ▼
IncidentRepository.get()
      │
      ├── found      → Mapper → Incident → 200
      └── not found  → 404
```

# 🧩 Key Design Decisions

## Separate DTO and ORM Models

```text
Incident (Pydantic)         IncidentRecord (SQLAlchemy)
API / domain contract       Database row mapping
Validation rules            Columns, constraints, indexes
```

A schema change does not leak into the API contract, and the reverse. The cost is an explicit mapping step.

## Transaction Boundary

```text
Repository  →  flush only
get_session →  commit / rollback
```

One request is one transaction, similar to `@Transactional` on a service in Spring.

## String + CHECK Instead of a Native ENUM

Severity and status are stored as strings with `CHECK` constraints generated from the Python enums. This keeps integrity in the database while avoiding the migration pain of changing a native PostgreSQL ENUM.

## PostgreSQL + Qdrant Instead of pgvector

Qdrant provides built-in dense + sparse hybrid search and payload filtering. The trade-off is two stores to keep in sync, which is why PostgreSQL remains the source of truth.

# ▶ Getting Started

## 1. Install

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## 2. Create the database

```bash
createdb opsmind
```

## 3. Configure `.env`

```text
DATABASE_URL=postgresql+psycopg://<user>@127.0.0.1:5432/opsmind
```

## 4. Apply migrations

```bash
alembic upgrade head
```

## 5. Run the API

```bash
python -m uvicorn main:app --reload
```

Open `http://127.0.0.1:8000/docs` for the interactive API documentation.

## 6. Run the tests

```bash
python -m pytest
```

> The repository and API tests use the configured database but run inside a transaction that is rolled back, so they leave no rows behind.
